2. What a program actually is

A program is a list of instructions, followed one at a time, top to bottom — like a recipe. The computer doesn't understand anything about "games." It just does exactly what each line says, in order, extremely fast. Everything you'll learn below is really just different ways of controlling which lines run, and how many times.

A running game is a loop that does the same three things roughly 60 times every second: check what the player is doing (input), update where everything is (movement, scoring, collisions), and draw the current picture (output). Each pass through that loop is one frame. This "input → update → draw, repeat" pattern is the one idea underneath every game you've ever played, from Tetris to the biggest console releases. Keep it in mind — you'll see it structure everything below.

3. The building blocks of Python

Six ideas cover almost everything you'll read or write for a long time.

variable

A labeled box for a value

SPEED = 200 means "make a box called SPEED and put 200 in it." Later, box.x += SPEED * dt reads the number back out. Give variables names that say what they hold — future-you will thank you.

types

Different kinds of value

200 is a number (int). 3.5 is a decimal (float). "hello" is text (str). True/False is a yes/no (bool). (255, 0, 0) is a fixed-size group (tuple) — that's how colors are stored: red, green, blue.

if / elif / else

Do this, only when...

if pressed[pg.K_LEFT]: means "only run the next indented line if the left arrow is held." elif checks another condition if the first was false; else catches everything else.

loop

Repeat, on purpose

while running: repeats everything indented under it for as long as running stays True. for b in blocks: repeats once for every item in a list, one at a time.

list

An ordered collection

blocks = [] starts an empty list. blocks.append(x) adds something to the end. A falling-objects game is really just "a list of things, each moved down a little every frame."

function

A named, reusable recipe

pg.draw.rect(...) is a function someone else wrote — you just tell it what and where, it handles the how. You can write your own too: def spawn_block(): defines one; calling spawn_block() runs it.

Two more things that trip people up early: indentation (the spaces at the start of a line) is how Python knows what's "inside" an if or a loop — lines at the same indent level run together as a group. And dot notation — things like screen.fill(...) or box.x — means "reach inside this thing (screen, box) and use its fill or x." Almost everything in the game code is either a plain variable or something-dot-something.

4. Reading the example, line by line

Here's the exact code you ran in chapter 1, broken into pieces with what each one is doing. Have the Make page open in another tab and match these up against the real thing.

A

Setting the stage

import webgame as pg

WIDTH, HEIGHT = 400, 300
pg.init()
screen = pg.display.set_mode((WIDTH, HEIGHT))

import webgame as pg loads this site's drawing/input toolkit and gives it the short nickname pg. WIDTH, HEIGHT = 400, 300 sets two variables in one line. pg.display.set_mode(...) creates the canvas at that size and hands back a Surface — the thing you draw onto — stored in screen.

B

Things that can change

box = pg.Rect(WIDTH // 2 - 20, HEIGHT // 2 - 20, 40, 40)
SPEED = 200
color = (232, 163, 61)
elapsed = 0.0

This is the game's state — everything that can be different from one frame to the next. box is a rectangle (position + size) tracking the square. Notice SPEED never changes during play (a constant, by convention written in capitals) while color and elapsed do.

C

The loop itself

async def main():
    global color, elapsed
    running = True
    while running:
        dt = (await clock.tick(60)) / 1000.0
        elapsed += dt

while running: is the game loop — this repeats every frame until something sets running to False. clock.tick(60) waits for the next screen refresh and reports how much time actually passed, in milliseconds; dividing by 1000 converts that to seconds and stores it as dt ("delta time"). Every movement in the game is written as "distance per second times dt," which is why the square moves at the same speed no matter how fast or slow the computer running it is.

D

Input

for e in pg.event.get():
    if e.type == pg.QUIT:
        running = False
    if e.type == pg.KEYDOWN and e.key == pg.K_SPACE:
        color = (79, 184, 166) if color != (79, 184, 166) else (232, 163, 61)

pressed = pg.key.get_pressed()
if pressed[pg.K_LEFT]:
    box.x -= SPEED * dt

There are two different ways input shows up. pg.event.get() gives one-time notifications — "space was just pressed" — good for actions that should happen once per press. pg.key.get_pressed() gives the current held-down state of every key — good for continuous movement, since you want the square to keep moving the whole time a key is down, not just on the first frame.

E

Drawing

screen.fill((20, 23, 31))
pg.draw.rect(screen, color, box, border_radius=8)
label = font.render(f"t={elapsed:4.1f}s", True, (237, 233, 223))
screen.blit(label, (10, 10))

Drawing always goes in this order: clear the screen first (fill), then draw everything on top of that fresh background, every single frame — even things that "didn't move." There's no way to erase just one object; you redraw the whole picture instead. font.render(...) turns text into a small image; blit stamps that image onto the screen at a position.

6. Build a game from a blank canvas

Editing an existing game teaches you to read code. Building one from nothing teaches you to think in code — which is the actual skill. Type each step into the Make editor yourself rather than copy-pasting; typing it is what makes it stick. We're building Catch the Coins: a paddle at the bottom catches falling coins for points, and missing too many ends the game.

1

An empty window

Every game starts the same way — set up the window, then loop forever until told to stop:

import webgame as pg

WIDTH, HEIGHT = 400, 500
pg.init()
screen = pg.display.set_mode((WIDTH, HEIGHT))
clock = pg.time.Clock()

async def main():
    running = True
    while running:
        dt = (await clock.tick(60)) / 1000.0
        for e in pg.event.get():
            if e.type == pg.QUIT:
                running = False
        screen.fill((20, 23, 31))
    pg.quit()

await main()

Run it. You'll see a dark rectangle and nothing else — that's expected. This skeleton (setup, then loop with input-update-draw) is the shape every game in this guide shares.

2

Add the paddle

Before async def main():, add a rectangle to represent the player:

paddle = pg.Rect(WIDTH // 2 - 40, HEIGHT - 30, 80, 14)

Then, inside the loop, after screen.fill(...), draw it:

pg.draw.rect(screen, (232, 163, 61), paddle, border_radius=4)

Run it — a paddle sits at the bottom. It doesn't move yet, because nothing is reading input.

3

Move it

Right after the for e in pg.event.get(): block, read the keyboard and move the paddle:

pressed = pg.key.get_pressed()
if pressed[pg.K_LEFT]:
    paddle.x -= 320 * dt
if pressed[pg.K_RIGHT]:
    paddle.x += 320 * dt
paddle.x = max(0, min(WIDTH - paddle.width, paddle.x))

That last line stops the paddle from sliding off either edge — it clamps paddle.x between 0 and the furthest-right position that still fits on screen.

4

Add one falling coin

Near the paddle line, add a coin and its speed:

coin = pg.Rect(WIDTH // 2 - 8, 0, 16, 16)
coin_speed = 150

In the loop, after the paddle movement code, move the coin down and draw it:

coin.y += coin_speed * dt
pg.draw.circle(screen, (79, 184, 166), coin.center, 8)

Run it — one coin falls straight through the bottom and disappears forever. That's the next problem to solve.

5

Make it respawn

Right after moving the coin, check whether it fell off the bottom, and if so, send it back to the top at a random x position:

import random

(add that import at the very top of the file, next to import webgame as pg). Then, after coin.y += coin_speed * dt:

if coin.y > HEIGHT:
    coin.y = -16
    coin.x = random.randint(0, WIDTH - 16)

Now the coin falls forever, reappearing at a new spot each time it reaches the bottom.

6

Catch it — collision and score

Add a score variable near the top: score = 0. Real games check "is the player touching the object" every frame — Rect already knows how to answer that with colliderect. Replace the respawn check with:

if coin.colliderect(paddle):
    score += 1
    coin.y = -16
    coin.x = random.randint(0, WIDTH - 16)
elif coin.y > HEIGHT:
    coin.y = -16
    coin.x = random.randint(0, WIDTH - 16)

score needs global score added at the top of async def main():, same as color did in the first example — any variable defined outside a function that gets changed inside it needs to be declared global first.

7

Show the score

Set up a font once, outside the loop: font = pg.font.SysFont("monospace", 20). Then, after drawing the paddle and coin:

label = font.render(f"score: {score}", True, (237, 233, 223))
screen.blit(label, (10, 10))

Run it — catch coins, watch the number climb. This is already a real, playable game.

8

Add lives and a game over

Add lives = 3 near score (and add it to the global line too). In the miss branch (elif coin.y > HEIGHT:), subtract a life instead of nothing:

elif coin.y > HEIGHT:
    lives -= 1
    coin.y = -16
    coin.x = random.randint(0, WIDTH - 16)
    if lives <= 0:
        running = False

Show it next to the score: f"score: {score} lives: {lives}". Now missing three coins ends the game — you've just built a complete win/lose condition, the same pattern behind every scored game that exists.

7. Challenges with no answers given

Pick whichever sounds fun. Skipping around is fine.

EASIER

  • Make the paddle move faster when a key called pg.K_LSHIFT is held.
  • Make the coin a different color each time it respawns.
  • Make the falling speed increase slightly every time a coin is caught.

MEDIUM

  • Add a second coin, falling independently, using its own variables (or, if you're feeling bold, a list of coins).
  • Add a "game over" message that appears once lives reaches 0, instead of the game just quietly stopping.
  • Add a key that resets score and lives back to their starting values without reloading the page.

HARDER

  • Rewrite the single coin as a list of coins, spawning a new one every couple of seconds (look at how games/dodger/main.py on the Games page does this for falling blocks).
  • Make coins fall at slightly different, random speeds, so they don't all move in sync.
  • Add a "bad" object (a different color) that costs a life if caught instead of a point — now the player has to make quick decisions, not just react.

8. When something goes wrong

Every beginner hits these. They're not a sign you did something badly wrong.

IndentationError

Python cares about spaces at the start of a line. If a line inside an if or while isn't lined up with the lines around it, fix the spacing so it matches.

SyntaxError: expected ':'

Lines that start a block — if, while, for, def — need a colon at the end. Easy to forget.

NameError: name 'x' is not defined

You used a variable before creating it, or misspelled its name. Check the spelling matches exactly, including capital letters.

SyntaxError: name 'score' is used prior to global declaration

Any variable set outside a function that you plan to change inside async def main(): needs global that_name as the very first line of the function, before it's used.

Nothing seems to happen when you click Run

Check the text next to the Run button says "ready," not "loading" or "failed." The engine takes a couple seconds to load the first time.

9. Glossary

variable
A named place to store a value that can change.
function
A named, reusable block of instructions you can run by writing its name followed by parentheses.
loop
Code that repeats — while repeats based on a condition, for repeats once per item in a collection.
condition
A statement that's either True or False, used by if to decide whether to run some code.
indentation
The spaces at the start of a line, which Python uses to know what's "inside" a loop, function, or if.
Rect
A rectangle — position plus width and height — used here for anything that needs a location and a size: the player, coins, obstacles.
Surface
Something you can draw onto — the screen itself is one; you can also make offscreen ones.
frame
One pass through the game loop — one "tick" of input, update, and draw. Games usually run around 60 frames per second.
delta time (dt)
How much real time passed since the last frame, used so movement speed stays the same regardless of how fast the computer is running the game.
collision detection
Checking whether two things overlap — colliderect answers this for two rectangles.
state
Everything about the current situation that can change over time — score, position, lives, whether the game is over.
